# 录制与低配版验收记录（2026-10-28）

本轮实现 BililiveRecorder 2.20.0 接入、默认320p/可选高清、受限CPU推理、多人独立草稿及资源预算。代码保存于 `feat/bililive-low-resource` 评审分支，未合并主分支，未发布新的桌面安装包。

## 已验证

- 完整后端回归246项通过，1项可选训练测试跳过；包含部署脚本、容器账户配置及排队期间模型变更的回归。
- 前端49项测试通过，TypeScript/Vite生产构建成功。
- 真实FFmpeg FLV → 认证FileClosed → 去重/共享项目 → 后台320p → editor克隆：自动集成测试通过；原片哈希保持一致，不复制完整原片。
- 录制REST采用本机HTTP模拟服务，验证添加/开始/停止、事件幂等、文件稳定性、重启恢复、密钥、路径限制及磁盘暂停逻辑。
- 公开官方配置DTO与REST源码核对后实现回调自动设置；测试覆盖保留无关回调、密钥更新、幂等和读取确认。
- 实际浏览器：录播库开始/停止控件，文件入库后打开，默认媒体高度320，切换后高度1080，播放位置保留；已保存草稿可正常导出。
- 浏览器合成片段从1秒到4秒精确导出，视频为1920×1080、时长3.000秒，MP3正常；快速复制示例因关键帧包含额外起始内容，视频4.088秒，界面明确区分快速与精确。
- 快速导出测试检查编码包哈希仍来自源片；精确导出测试核对请求时长。
- 同参数跨用户导出复用媒体字节，各自保留独立项目快照与下载权限。
- CPU流式worker使用真实LogMel和CRNN，同窗口配置与原实现概率差≤1e-6；覆盖窗口接缝、二/多分类、尾段与65秒完整CPU子进程。不同窗口长度的真实识别精度不据此推定相同。
- 实际子进程的取消、截止时间、异常和子进程树清理；持久任务重启、队列上限、按用户轮换、账户隔离与会话令牌绑定。
- 无Content-Length的上传在multipart写入过程中被限制，部分临时文件关闭；媒体连接、编码后的高清参数及共享发送预算受控。
- 390px录播库无横向溢出；常规桌面可查看清晰度、录制状态与导出入口。
- 部署脚本通过模拟Docker命令验证一键录制参数、凭据保留、私有文件权限及回调失败不谎报成功；Compose YAML检查无重复键，shell语法检查通过。

## 本轮未宣称完成的验证

本机没有Docker命令，也未取得目标Linux主机连接，因此没有执行真实容器部署或弱CPU容量压测。本轮未使用B站Cookie或开启真实直播录制，录播事件验证使用隔离合成素材和本机模拟服务。正式上线需在实际主机核对画质权限、长录播的峰值内存、CPU耗时、录制稳定性及多人带宽。

服务器默认关闭训练，本机正常模式继续保留训练。现有模型输出演唱区间；歌名/歌词参考库识别不是本轮功能。素材当前必须完成分段落盘后导入，不读取仍在写入的文件。

## 使用入口

- 本地仍使用用户指定的8777端口。
- Linux：`./scripts/deploy.sh --recorder`；域名可追加 `--domain songs.example.com`。
- 多人独立账号：创建被Git忽略的 `server-accounts.json`，参见 [低配与多人配置](LOW-RESOURCE-SERVER.md)。
- 首次录制：打开“录播库”添加房间；所需B站Cookie由管理员在独立录播姬设置中配置。
